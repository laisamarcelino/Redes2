1. RESUMO DOS REQUISITOS DO SISTEMA
--------------------------------------------------------------------------------
- Componentes:
  1. Load Balancer (LB): Intermediador TCP concorrente com políticas Round-Robin e Least Connections.
  2. Servidores Backend (N instâncias): Atendem requisições repassadas pelo LB de forma concorrente e respondem com "OK". Podem falhar e ser recuperados.
  3. Sistema de Monitoramento: Checa a integridade dos servidores periodicamente e atualiza o estado (UP/DOWN).
  4. Tabela de Servidores: Armazena IP, porta, status (UP/DOWN), conexões ativas e total de conexões.
  5. Script de Clientes: Gera tráfego concorrente simulando M clientes com conexões de K segundos.
- Restrições técnicas:
  * Utilizar exclusivamente sockets TCP padrão (sem bibliotecas adicionais de rede).
  * Clientes conhecem apenas o LB (não podem conectar diretamente aos servidores).
  * Deve executar obrigatoriamente no ambiente dos servidores do DInf.
  * Linguagem livre (sugestão: Python ou C).
  * Relatório em LaTeX com no máximo 4 páginas.
  * Entrega: arquivo .tgz (código-fonte) + relatório em PDF.
  * Defesa oral obrigatória (nota multiplicativa).

FASE 4: IMPLEMENTAÇÃO DO LOAD BALANCER (LB)
--------------------------------------------------------------------------------
[X] Passo 4.1: Inicialização e Parâmetros de Linha de Comando (`lb.py`)
    - Parâmetros obrigatórios:
      * Porta de escuta do LB.
      * Política de balanceamento: `round-robin` ou `least-connections`.
      * Lista de servidores backend (arquivo de configuração ou argumentos no formato IP:PORTA).
    - Validação dos argumentos e inicialização da Tabela de Servidores.

[X] Passo 4.2: Implementação das Políticas de Escolha
    - **Round-Robin**:
      * Manter um ponteiro/índice circular de seleção.
      * Filtrar apenas servidores com status UP.
      * Avançar de forma circular e atômica para garantir distribuição equilibrada.
    - **Least Connections**:
      * Filtrar apenas servidores com status UP.
      * Selecionar o servidor com a menor quantidade de conexões ativas no momento.
      * Em caso de empate, aplicar desempate estável (ex: menor ID ou round-robin entre os empatados).

[X] Passo 4.3: Concorrência e Proxy de Tráfego (Relay Bidirecional)
    - Socket listener TCP principal atendendo novas conexões de clientes.
    - Para cada conexão recebida:
      1. Disparar uma thread trabalhadora para não bloquear novas conexões.
      2. Consultar a Tabela de Servidores e aplicar a política configurada para escolher um servidor ativo.
      3. Se nenhum servidor estiver ativo: retornar erro/fechar conexão e logar alerta.
      4. Incrementar contador de conexões ativas do servidor escolhido na Tabela.
      5. Estabelecer socket TCP de saída em direção ao servidor escolhido.
      6. Repassar fluxo bidirecional de dados:
         - Cliente -> LB -> Servidor
         - Servidor -> LB -> Cliente
      7. Ao finalizar a conexão (cliente encerrou ou socket quebrou):
         - Fechar sockets com segurança.
         - Decrementar contador de conexões ativas na Tabela.

      * Notificações de mudança de status (Servidor DOWN / Servidor UP).

--------------------------------------------------------------------------------
[ ] Passo 6.1: Cenário 1 - Teste da Política Round-Robin

    - Disparar 30 conexões de clientes com tempos uniformes.

[ ] Passo 6.2: Cenário 2 - Teste da Política Least Connections

    - Disparar clientes com tempos de conexão heterogêneos (ex: alguns clientes com K=10s e outros com K=1s).
    - Verificar se novas conexões foram direcionadas para os servidores com menor carga acumulada no momento.

[ ] Passo 6.3: Cenário 3 - Teste de Tolerância a Falhas
    - Com carga de clientes em execução, derrubar forçadamente um dos servidores (matar processo ou comando de falha).
    - Verificar se o Monitoramento detectou a queda e marcou o servidor como DOWN.
    - Verificar se o LB parou de encaminhar novas requisições para o servidor caído e continuou atendendo nos demais.

[ ] Passo 6.4: Cenário 4 - Teste de Recuperação de Falhas
    - Reiniciar o servidor caído na mesma porta.
    - Verificar se o Monitoramento identificou a reativação e atualizou a tabela para UP.
    - Verificar se o LB voltou a enviar tráfego para esse servidor normalmente.
